# Ralph planning and recovery

An owner can give a coding app a plain-language goal, review the proposed work once,
and start it without constructing a job file or checkout by hand. This uses
the app's terminal tool and the ordinary Excubitor CLI. It installs no
hooks, slash commands, MCP servers, or machine services.

## Normal workflow

Ask the coding app to run `ralph plan` with the goal, project, and reusable host profile.
The command creates a separate local clone, copies the selected existing tests,
and asks the selected model adapter for structured work units. It prints a preview and
starts no implementation. The original requested goal is retained verbatim. Related
changes are grouped into implementation units, and at least half the attempt
budget is reserved for retries when the budget allows it.

```text
python -B -m excubitor.cli ralph plan --project D:/projects/example --profile D:/settings/example.json --root D:/jobs/example-fix --goal "Fix the requested behavior"
```

The coding app should show the preview, explain the acceptance checks, and wait for the
owner's approval. After approval, it can invoke:

```text
python -B -m excubitor.cli ralph start --plan D:/jobs/example-fix --baseline native-development-v1 --background
python -B -m excubitor.cli ralph status --root D:/jobs/example-fix/run
python -B -m excubitor.cli ralph stop --root D:/jobs/example-fix/run
```

The start command is the authorization boundary, as with an ordinary owner-run
CLI. Calling it from an agent relies on that agent respecting the owner's approval;
this terminal integration does not attest a native confirmation dialog.
The original prepared-job form of `start --job ... --root ...` remains available.

## Reusable host profile

The profile holds `git`, `llm`, `executor`, `editable`,
`checks`, `check_files`, `max_attempts`, `time_limit_seconds`, and `retain_command`.
These have the same meanings as the prepared-job CLI fields, with two conveniences:

- `check_files` lists project-relative existing acceptance implementation files.
  Planning copies them outside the candidate so later edits cannot weaken them.
- Check arguments can use `{checks}` for that copied test directory and
  `{candidate}` for the automatically created checkout.


The coding app that launches the command, the model that does the work, and the
executor that runs tests are separate choices. Changing the app does not require
rewriting the loop. These model descriptors can be swapped before preparing a
new agreement:

```json
{
  "llm": {
    "adapter": "claude-cli",
    "executable": "D:/Tools/ClaudeCode/claude.exe",
    "model": "claude-sonnet-5"
  },
  "executor": {
    "adapter": "codex-windows",
    "executable": "C:/path/to/codex.exe",
    "home": "D:/path/to/existing-codex-home"
  }
}
```

For Codex, replace only the `llm` descriptor:

```json
{
  "adapter": "codex-cli",
  "executable": "C:/path/to/codex.exe",
  "home": "D:/path/to/existing-codex-home",
  "model": "gpt-6-astra"
}
```

These are descriptor examples, not complete profiles. Use the actual installed
executable, existing login directory, and an available explicit model. An
unsupported adapter or missing executable is rejected before planning. Legacy
profiles containing `claude`, `codex`, `codex_home`, and `model` still select the
original Claude model and Codex Windows executor. Saved legacy run settings are
read without rewriting their agreement. Mixing the two formats is rejected.

The selected model and executor are saved in the reviewed plan and run. Resume
cannot silently switch either or increase the original limits.

The profile is selected by the owner, not generated by the planner. It is reusable
for jobs in the same project. The host must provide an authorized committer that
supports the new candidate; planning does not grant broker enrollment or supply a
direct-Git fallback. Changes to tests or permitted files require a deliberate
profile update before the next plan. New behavior needing new acceptance tests
must have those tests prepared and reviewed first.

Planning currently requires a clean original Git checkout and the development
adapter's bounded set of existing editable files. It preserves dirty originals
by refusing preparation. No fetch, push, merge, or original-branch change occurs.
Private planning directories retain unsuccessful attempts for diagnosis.

## Recovery

Every controller now runs under the existing named Windows-job watchdog. A
controller crash drains its descendants and restarts within the original attempt
and time limits. There are at most three controller launches across watchdog
lifetimes. A handled runtime or commit refusal is preserved and is not retried as
if it were a crash.

With `--background`, a detached watchdog continues after an ordinary calling
terminal exits. If the watchdog itself is lost, reconnect using:

```text
python -B -m excubitor.cli ralph resume --root D:/jobs/example-fix/run --background
```

Resume checks the saved settings and frozen tests, reconciles the previous named
job, preserves crash journals, and continues the same agreement. It neither
refreshes the deadline nor grants more attempts. Jobs created before watchdog
support do not acquire recovery evidence retroactively. Host logout, reboot, and
parent environments that forcibly terminate detached descendants require a later
resume; no automatic machine-start service is installed.

## Native evidence

The Windows rehearsal used Claude Sonnet 5 after Fable reported its usage limit
before planning began. Native Claude's Bash tool invoked planning, displayed the
preview without starting work, and later invoked background start for the reviewed
test job. The background run completed two Python statistics fixes, frozen tests,
and fresh independent review after the launching Claude command returned. The
original repository and copied check stayed unchanged. This exercised a small
disposable Git repository with runnable source and acceptance tests, not a mock
worker or a production rollout.

A separate run deliberately killed one active controller, then killed its
replacement watchdog. Automatic controller recovery and subsequent `resume`
completed both units and fresh review in four charged attempts. The same agreement
and original deadline survived both faults. The history recorded three controller
launches and one named-job reconciliation after watchdog loss. Fault injection
lives only in the private test harness.

## Adapter boundaries

`development_runtime.py` owns snapshots, edit validation, applying edits,
verification, and review verdict handling. A structured model implements
`generate(run, prompt, schema, cancel)` and returns a native process result plus
a proposal. It does not own completion, commits, or the retry loop. The shared
runtime discards proposals from incomplete, cancelled, or undrained calls.

`development_adapters.py` selects the model and executor independently from
host-owned descriptors. New adapters belong at this boundary; they should reuse
the same planner, supervisor, checks, and recovery tests. Unknown adapters never
silently fall back to another vendor.

Claude advertises only its structured-output tool. Codex uses read-only mode,
disables its shell tool, and requests a JSON schema; its adapter accepts only a
completed native response with no tool events. This is a development workflow,
not a claim that both native tool systems have identical security guarantees.
The Codex shell setting is documented in the official
[configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference).

The launcher now also supports `command-json` for a host-selected model client and
`chat-completions` for a compatible HTTP endpoint. Both return proposals to the
same runtime. `windows-process` provides vendor-independent execution for trusted
local projects under the explicit `trusted-local-v1` baseline. It manages process
lifetimes without filesystem or network isolation; it is never fallback for a
refused sandbox request. `codex-windows` keeps its existing baseline and behavior.

See the [quickstart](../ralph-quickstart.md) for complete settings. The HTTP client
uses the documented [Chat Completions request and response format](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create),
also implemented by [compatible local servers](https://docs.ollama.com/api/openai-compatibility).
Endpoint and model capabilities differ. Select a supported JSON response format;
the client does not silently switch models or providers. Local protocol tests are
not evidence that every hosted/local model is supported. Linux launcher
integration and dedicated app shortcuts remain unverified.

## Persistence across fresh contexts

The host retains compact continuation data outside candidate files and rotating
watchdog journals. A replacement controller reloads the last actionable worker,
check, or review feedback. The next model call receives the original agreement,
current source, remaining work and budget, and recent host observations. No chat
transcript is needed. The run store remains the sole completion authority.

Fresh calls are currently the default at each bounded step. Research does not
establish one universal restart interval: multi-turn underspecification can
increase unreliability, while long-running harness results vary by model.
See [multi-turn experiments](https://arxiv.org/abs/2505.06120) and
[model-dependent harness results](https://www.anthropic.com/engineering/harness-design-long-running-apps).
Per-call prompt size, elapsed time and outcomes are recorded alongside host phase
observations. These measurements support later calibration; the implementation
does not pretend to detect statistically proven model fatigue from a few turns.

## Shared-runtime Windows comparison

Native Codex and Claude each completed the same statistics task with unchanged
acceptance tests and a fresh review through this shared runtime. Each successful
run completed three units in three attempts. A Codex recovery run also completed
after an injected controller crash and watchdog loss: five attempts, three
controller launches, and the original agreement and deadline preserved. A
separate Codex stop drained the active process tree in less than one second.

The first Claude comparison plan split the task into six units and exhausted
eight attempts while running full-suite commands before later units were ready.
That failed run remains preserved. The shared planning prompt and unit limit now
reserve room for retries and ask for cohesive changes. A fresh plan with the same
model, acceptance, and limits completed. This is evidence from a small disposable
project; it does not establish reliability for arbitrary repositories or models.
